# arXiv 批量采集脚本：完成报告

> 日期：2026-10-29 ｜ 文件：`scripts/arxiv_ingest.py`、`tests/test_arxiv_ingest.py` ｜ 全量 363 passed
> 目的：让「论文入库」不只靠管理员逐个上传 PDF，可以从 arXiv 按分类/关键词批量灌数据。

## 结论

可以。arXiv 官方 Atom 接口（`export.arxiv.org/api/query`）无需 key，按分类 + 关键词检索；
脚本负责检索、下载 PDF、调用**现有管理员导入接口**入库，并用 arXiv 元数据修正标题/作者/年份/来源/摘要。

没有绕过任何既有约束：走的还是 `/api/v1/admin/papers/import` 同一条流水线
（SHA-256 去重 → PDF 解析 → 切块 → 向量），所以库里数据形态与手工上传完全一致。

## 实现

| 部分 | 说明 |
| --- | --- |
| 检索 | `build_search_query()` 组合 `cat:<分类>` 与 `all:"<短语>"`；`--sort submittedDate/relevance/lastUpdatedDate`，`--start` 翻页 |
| 解析 | `parse_atom()` 用 `xml.etree` 解析 Atom：id（去版本号）、标题、作者（≤50）、年份、摘要（≤20000）、PDF 链接、`arxiv:doi`、`arxiv:journal_ref`、分类 |
| 下载 | 逐篇 `urllib` 下载 PDF，文件名 `{arxiv_id}.pdf`；每请求后 `--delay`（默认 3s） |
| 导入 | `build_multipart()` 手工拼 multipart，按 `--batch-size`（≤20）/100MB 上限分批；超过 100MB 自动拆成单个导入 |
| 元数据 | 导入返回的 `paper_id` → 轮询 `GET /admin/papers/{id}` 到离开处理中（契约：处理中 PATCH 409）→ `PATCH` 标题/作者/年份/摘要/来源 |
| 幂等 | 重复运行命中 SHA-256 判重，服务端返回 `duplicate`，脚本打印“已存在”且不再修正元数据 |
| 依赖 | 只用标准库（`urllib`/`xml.etree`/`json`/`argparse`），没有新增运行时依赖 |

CLI：`--category`（默认 `cs.*`）、`--query`、`--max-results`（1–500）、`--start`、`--sort`、
`--batch-size`、`--delay`、`--wait`/`--poll-interval`、`--base-url`、`--email`/`--password`
（或 `PAPERLENS_ADMIN_EMAIL/PASSWORD`）、`--no-metadata`、`--dry-run`。

## 踩到并修掉的四个真实问题

1. **Cookie 取不到**：`dict(response.headers)` 会把键小写成 `set-cookie`，而代码读 `Set-Cookie` →
   登录报“没有拿到 paperlens_session”。改为统一 `_lower_headers()` 归一化。
2. **元数据修正 409**：导入返回 `queued`，后台立刻开始解析，PATCH 因“处理中”被拒。
   改为轮询 `GET /admin/papers/{id}` 到 `ready` 再 PATCH（`--wait` 控制上限）。
3. **arXiv CDN 按连接限速**（实盘灌 100 篇才暴露）：单条 TCP 连接会被随机压到 ~11–18KB/s，
   换一条新连接又能跑到 ~1MB/s；请求头（`Connection: close` / keep-alive）与出口 IP 都无关，
   只和“这一条连接”有关。原来的下载会一路等到 120s 超时，50 篇要跑上小时。
   现在 `Http.get_bytes()` 分块读、按**平均速率**判断：观察满 `DOWNLOAD_SLOW_SECONDS=10s` 后
   仍低于 `DOWNLOAD_MIN_BYTES_PER_SEC=100KB/s` 就主动断开、换连接重试（最多 `DOWNLOAD_ATTEMPTS=5` 次）。
   实测单篇从“卡 120s 后失败”变成“0.5s 下完 495KB”。
4. **PDF 抽出孤立代理项导致入库崩溃**：个别 PDF 的 ToUnicode 映射是坏的，pypdf 会抽出
   `\ud800-\udfff` 孤立代理项，`content_hash` 的 `content.encode("utf-8")` 直接抛
   `UnicodeEncodeError`，论文永远停在 `failed`（重试也没用）。在 `normalize_text()` 里
   统一剔掉这些字符，解析、切块、入库都跟着修好（`REGER` 那篇 88 chunks 正常入库）。

## 编号与计数怎么看（答疑：为什么最后一页从 4 开始、为什么是 98 篇不是 101 篇）

后台列表按 `created_at desc, id desc` 排序，页面上的编号是 `papers.id`（自增主键），
**不是「第几篇」**，所以会出现「最后一页第一行是 4」这种看着不对、其实正常的情况：

- 库内 98 条 = id **4 ～ 101 连续**，`lag(id)` 逐行比对 **0 个空洞**（只有 1/2/3 三个号整体缺失）；
- id 1、2、3 是 12:19 之前手工上传测试后被删掉的行（现存日志已不在，无法回溯是谁删的；
  但可以确定是「正常删除」而不是残留：目录不存在、无悬垂引用），MySQL 自增**不回退**，这三个号就空了；
  `var/papers/1`、`2`、`3` 也不存在（没有残留文件），
  `session_papers`/`session_evidence`/`repo_papers`/`paper_files`/`paper_summaries` 对已删论文的悬垂引用全为 0；
- id 4、5、6、7 就是最早的 4 篇演示论文（`created_at` 12:19），排序在最后，
  即「第 5/5 页」的最后 4 行——它们没丢，只是按时间排到了末尾；
- 所以「最大 id 101」≠「101 篇」，实际 **98 篇**（`20 × 4 + 18 = 98`，页脚「共 98 条 · 第 5/5 页」是对的）。

要「从 1 连续编号」只能在显示层做（行号 = `(page-1)*page_size + i + 1`）：主键被
`paper_files`/`paper_chunks`/`session_papers`/`repo_papers`/`paper_summaries` 外键和
`var/papers/<id>/` 目录名同时引用，重排主键没有收益、风险高，本轮**不动数据、不改代码**。

## 已知边界

- 只支持 arXiv（Atom 接口）；其他来源（Semantic Scholar、OpenAlex）未接入。
- arXiv 有访问频率约定，脚本默认 3 秒间隔，批量大会慢（50 篇 ≈ 10 分钟，含解析与向量化）。
- CDN 按连接限速是随机的，重试 5 次仍有极少数篇会失败（本轮 100 篇里 2 篇），
  按标题单篇补一次即可，不影响整体批次。
- 需要服务处于运行状态（走 HTTP 契约，不直接写库）；解析/向量化是后台任务，脚本只等元数据修正。
- 采集的 PDF 存在 `PAPER_STORAGE_DIR`，不占用数据库；重复运行不会重复占空间（判重后丢弃）。
