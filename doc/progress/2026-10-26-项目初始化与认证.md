## 1. 项目背景与当前阶段

PaperLens 是一个论文知识库问答平台。V1.0 产品文档将系统划分为四个空间：

| 空间 | 作用 |
| --- | --- |
| 全局论文目录 | 管理员维护的全部论文，是搜索的唯一来源 |
| 会话 | 一次查询得到的论文、证据和对话 |
| 仓库 | 用户从全局目录挑选的论文集合 |
| 论文详情 | 单篇论文的元数据、四维、原文和单篇对话 |

产品文档的 V1.0 范围包括账户、论文目录、搜索、仓库、论文展示、对话和管理后台。本记录点只完成了其中的 **账户基础能力与后端工程底座**，为后续业务模块提供可复用、可迁移、可测试的基础。

需要特别记录的边界：

- 产品文档规定 **账号由管理员创建，不开放自注册**。
- 当前代码为了本地开发和测试方便，提供了公开的 `POST /api/v1/auth/register`。
- 因此，当前注册接口属于开发阶段能力，后续必须按产品规则收紧为管理员创建用户，或至少在进入 V1.0 验收前明确处理方式。

**结果**：接口错误格式一致，日志可追踪单次请求，配置与业务代码解耦。

### M3：数据库访问层

- `app/db.py` 提供异步 engine、session factory 和 `get_db()` 依赖。
- 生产/本地使用连接池并配置 `pool_pre_ping`、`pool_recycle=3600`。
- 测试环境使用 `NullPool`，避免异步测试事件循环之间复用连接。
- `Settings.resolved_database_url()` 根据 `APP_ENV` 选择开发库或测试库。
- 通过 `reset_engine()` 支持测试和关闭时释放连接。

**阶段性返工**：最初使用 `Base.metadata.create_all()` 在应用启动时建表，后来改为 Alembic。原因是 `create_all` 没有版本记录，无法安全演进 schema，也不适合生产部署。

### M4：账户认证

实现四个接口：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v1/auth/register` | 注册并创建会话 |
| POST | `/api/v1/auth/login` | 登录并创建会话 |
| POST | `/api/v1/auth/logout` | 退出并撤销当前会话 |
| GET | `/api/v1/auth/me` | 返回当前登录用户 |

认证采用 HttpOnly opaque session cookie，不使用 JWT：

- 登录成功后生成随机令牌。
- 数据库只保存令牌的 SHA-256 哈希，不保存明文令牌。
- 浏览器 Cookie 保存明文令牌，设置为 HttpOnly。
- 服务端通过 Cookie 查 `user_sessions`，校验过期时间和用户状态。
- 密码使用 Python 标准库 `hashlib.scrypt` 哈希，参数为 `N=2^14, r=8, p=1, dklen=32`。

**结果**：账户主流程可用，密码和会话令牌不会以明文形式落库。

### M5：测试与质量基线

- 使用 httpx `ASGITransport` 直接调用 ASGI 应用，不启动真实端口。
- 测试固定使用 `TEST_DATABASE_URL`，并强制库名必须为 `paperlens_test`。
- 测试会话开始时重建测试库 schema，每个测试前清空业务表。
- 覆盖健康检查、请求 ID、错误响应、注册、重复邮箱、登录、退出、错误密码、未登录访问、短密码校验。
- 当前共 13 个测试通过。

**结果**：核心认证行为和工程基础能力有回归保护。

### M6：Alembic 接管 schema

- 引入 Alembic，新增 `alembic.ini` 与 `migrations/`。
- `migrations/env.py` 使用异步 engine，并从应用配置读取数据库连接串。
- 支持 pytest 注入已有同步 `Connection`，测试与 CLI 共用同一套迁移逻辑。
- 新增初始迁移 `migrations/versions/0001_auth_tables.py`。
- 删除 `app/db.py` 中的 `init_db()` 和 `create_all` 调用。
- 应用启动不再自动建表，部署流程必须先执行 `alembic upgrade head`。
- 测试会话改为删除表后执行 `alembic upgrade head`，因此测试同时验证迁移脚本。
- 开发库 `paperlens` 使用 `alembic stamp head` 建立基线，未执行破坏性重建。


### 5.2 统一错误格式

```json
{

    "code": "validation_error",
    "message": "请求参数不合法",
    "details": [
      {
        "field": "body.password",
        "message": "String should have at least 8 characters"
      }
```

已定义的默认映射：

| 状态码 | code | 消息 |
| :---: | --- | --- |
| 400 | `bad_request` | 请求不合法 |
| 401 | `unauthorized` | 请先登录 |
| 403 | `forbidden` | 无权访问 |
| 404 | `not_found` | 资源不存在 |
| 405 | `method_not_allowed` | 请求方法不允许 |
| 409 | `conflict` | 资源冲突 |

### 5.3 认证接口细节

**注册** `POST /api/v1/auth/register`

- 请求字段：`email`、`password`、可选 `display_name`。
- 邮箱由 `EmailStr` 校验，入库前统一转为小写。
- 密码长度 8–128。
- `display_name` 长度 1–64；为空时使用邮箱 `@` 前部分。
- 重复邮箱返回 `409 email_taken`。
- 并发重复邮箱通过数据库唯一索引兜底，捕获 `IntegrityError` 后返回 409。
- 成功后创建用户和会话，设置 HttpOnly Cookie，返回 201。

**登录** `POST /api/v1/auth/login`

- 请求字段：`email`、`password`。
- 邮箱统一转小写后查询。
- 用户不存在或密码错误统一返回 `401 invalid_credentials`，不泄露账号是否存在。
- 已停用用户返回 `403 user_disabled`。
- 成功后创建新会话并设置 Cookie。

**退出** `POST /api/v1/auth/logout`

- 需要有效会话。
- 删除当前 `user_sessions` 记录。
- 删除浏览器 Cookie。
- 返回 204。

**当前用户** `GET /api/v1/auth/me`

- 需要有效会话。
- 返回 `id`、`email`、`display_name`、`is_active`、`created_at`。
- 不返回 `password_hash` 或会话令牌。

### 5.4 健康检查

- `live` 只返回进程存活信息，不访问数据库。
- `ready` 执行 `SELECT 1`，数据库不可用时返回 `503 database_unavailable`。
- 当前 `ready` 只验证连接可用，**不验证 schema 版本是否已迁移到 head**。

## 6. 数据模型

### 6.1 `users`

| 字段 | 类型 | 约束/默认值 | 说明 |
| --- | --- | --- | --- |
| `id` | BigInteger | PK, autoincrement | 用户 ID |
| `email` | String(255) | 非空, 唯一索引 | 登录邮箱，入库时小写 |
| `password_hash` | String(255) | 非空 | scrypt 哈希字符串 |
| `display_name` | String(64) | 可空 | 展示名称 |
| `is_active` | Boolean | 非空, 应用层默认 True | 是否可登录 |
| `created_at` | DateTime | 非空, 应用层默认 UTC now | 创建时间 |
| `updated_at` | DateTime | 非空, 应用层默认/更新 UTC now | 更新时间 |

索引：

- `ix_users_email`：唯一索引。
- 主键 `id`。

### 6.2 `user_sessions`

| 字段 | 类型 | 约束/默认值 | 说明 |
| --- | --- | --- | --- |
| `id` | BigInteger | PK, autoincrement | 会话 ID |
| `user_id` | BigInteger | 非空, FK → `users.id` | 所属用户 |
| `token_hash` | String(64) | 非空, 唯一索引 | 会话令牌 SHA-256 |
| `expires_at` | DateTime | 非空, 索引 | 过期时间 |
| `created_at` | DateTime | 非空, 应用层默认 UTC now | 创建时间 |

约束与索引：

- 外键约束：`user_id` → `users.id`，`ON DELETE CASCADE`。
- `ix_user_sessions_user_id`：普通索引。
- `ix_user_sessions_token_hash`：唯一索引。
- `ix_user_sessions_expires_at`：普通索引。

### 6.3 时间与默认值约定

- MySQL `DATETIME` 存储 **naive UTC**，由 `app/core/time.py` 的 `utcnow()` 生成。
- `created_at` / `updated_at` / `is_active` 使用 SQLAlchemy 应用层默认值，不是数据库 server default。
- 这意味着绕过 ORM 直接写 SQL 时必须显式提供非空时间字段。
- 会话有效期由 `SESSION_TTL_DAYS` 控制，默认 7 天。

### 6.4 迁移状态

- 当前迁移 head：`0001_auth_tables`。
- `0001_auth_tables` 创建 `users`、`user_sessions` 及上述索引。
- `downgrade()` 先删除 `user_sessions`，再删除 `users`；索引随表删除。
- 开发库和测试库都已有 `alembic_version` 表。
- 开发库通过 `alembic stamp head` 建立基线，未执行 drop。
- 测试库在测试会话开始时由 `alembic upgrade head` 重建。

## 7. 认证与会话设计

### 7.1 注册流程

```text
POST /register
→ EmailStr 校验、密码长度校验
→ email 转小写
→ 查询邮箱是否已存在
→ scrypt 哈希密码
→ 插入 users
→ 生成随机 token
→ SHA-256(token) 写入 user_sessions
→ 设置 HttpOnly Cookie
→ 返回 201 + 用户信息
```

### 7.2 登录流程

```text
POST /login
→ email 转小写
→ 查询用户
→ scrypt 校验密码
→ 检查 is_active
→ 生成新 token
→ SHA-256(token) 写入 user_sessions
→ 设置 HttpOnly Cookie
→ 返回 200 + 用户信息
```

### 7.3 已登录请求

```text
Cookie: paperlens_session=<token>
→ get_current_session
→ SHA-256(token) 查询 user_sessions
→ selectinload(user)
→ 检查会话是否过期
→ 检查 user.is_active
→ get_current_user 返回 user
```

### 7.4 退出流程

```text
POST /logout
→ 校验当前会话
→ DELETE user_sessions 当前行
→ 清除 Cookie
→ 204
```

### 7.5 安全属性

- 密码使用 scrypt，数据库不保存明文密码。
- 会话令牌使用 `secrets.token_urlsafe(32)` 生成。
- 数据库只保存令牌哈希，泄露数据库不能直接复用 Cookie。
- Cookie 为 HttpOnly，默认 `SameSite=Lax`，本地默认 `Secure=False`。
- 登录失败不区分“用户不存在”和“密码错误”。
- 停用用户的已有会话在下次请求时也会被拒绝。

### 7.6 当前设计边界

- `users` 没有 `role` 字段，暂时无法区分普通用户与管理员。
- `POST /register` 当前公开可用，与产品文档“账号由管理员创建”不一致。
- 没有 CSRF token；当前依赖 SameSite 和同源前端。
- 没有登录失败次数限制、验证码或速率限制。
- 没有密码修改、忘记密码、重置密码。
- 没有会话滚动续期；登录 7 天后需重新登录。
- 没有过期会话清理任务；过期记录会保留在表中。
- 退出只撤销当前会话，不撤销该用户的其他设备会话。
- Cookie 的 `Secure` 在生产环境必须显式开启。

## 9. Alembic 迁移实现

### 9.1 文件与职责

| 文件 | 作用 |
| --- | --- |
| `alembic.ini` | Alembic 配置，`script_location = migrations` |
| `migrations/env.py` | 异步迁移环境、读取应用配置、注入连接 |
| `migrations/script.py.mako` | 新迁移模板，使用 Python 3.13 类型标注 |
| `migrations/versions/0001_auth_tables.py` | 初始认证表迁移 |

### 9.2 `env.py` 设计

- 使用 `create_async_engine()` 创建异步引擎，`NullPool` 避免连接复用问题。
- 从 `get_settings().resolved_database_url()` 获取连接串，不依赖 `alembic.ini` 里的占位 URL。
- `target_metadata = Base.metadata`，支持 autogenerate。
- 开启 `compare_type=True`，列类型变化可以被检测。
- 支持 CLI 模式：自己创建异步 engine。
- 支持 pytest 模式：读取 `config.attributes["connection"]`，在已有同步 `Connection` 上运行迁移。
- MySQL 不支持事务性 DDL，迁移结束后显式 commit，否则 `alembic_version` 可能不落库。
- PostgreSQL 等支持事务性 DDL 的数据库不额外 commit，避免提前结束外部事务。

### 9.3 初始迁移 `0001_auth_tables`

```text
revision: 0001_auth_tables
down_revision: None
```

`upgrade()`：

1. 创建 `users`。
2. 创建 `ix_users_email` 唯一索引。
3. 创建 `user_sessions`。
4. 创建 `user_id`、`token_hash`、`expires_at` 索引。

`downgrade()`：

1. 删除 `user_sessions`。
2. 删除 `users`。

### 9.4 应用启动行为

- 应用启动只做 `configure_logging()`。
- 关闭时执行 `reset_engine()`。
- 不再执行 `create_all()`。
- 数据库未迁移时，应用可以启动，但认证接口会因为表不存在而失败。
- 部署顺序必须是：**先 `alembic upgrade head`，再启动应用**。

### 9.5 测试中的迁移

测试不使用 `create_all`，而是：

```text
删除测试库现有表
→ DROP TABLE alembic_version
→ 注入同步连接
→ alembic upgrade head
→ 每个测试 DELETE 业务表
```

这样可以保证测试验证的是迁移脚本本身，而不仅仅是 ORM 模型。

### 9.6 常用命令

```bash
# 应用迁移
uv run alembic upgrade head

# 修改模型后生成迁移
uv run alembic revision --autogenerate -m "describe change"

# 查看/检查/回滚
uv run alembic current
uv run alembic check
uv run alembic downgrade -1

# 对测试库执行
APP_ENV=test uv run alembic current
APP_ENV=test uv run alembic check
```

### 9.7 已有数据库的处理

- 新库：直接 `upgrade head`。
- 之前用 `create_all` 建过空表、且 schema 与迁移一致的库：执行一次 `alembic stamp head` 建立基线。
- 当前开发库 `paperlens` 属于第二种，已 stamp 到 `0001_auth_tables`。
- 测试库 `paperlens_test` 由测试流程重建。

## 12. 已知差距与风险

### 12.1 与产品文档的差距

| 差距 | 当前状态 | 影响 |
| --- | --- | --- |
| 账号创建方式 | 开放 `POST /register` | 与“管理员创建账号、不开放自注册”冲突 |
| 角色模型 | `users` 无 `role` | 无法实现 reader/admin 权限矩阵 |
| 管理员初始化 | 无 | 没有第一个管理员，无法进入管理后台流程 |
| 用户管理 | 无 | 无法创建、停用、重置密码、分配角色 |
| 论文目录 | 无 | KB-01/KB-02 尚未开始 |
| 搜索/会话/仓库/对话 | 无 | V1.0 核心业务尚未开始 |
| 前端 | 无 | 产品页面和交互尚未实现 |

### 12.2 认证与安全风险

- 公开注册接口若保留到生产，会绕过管理员建号规则。
- 没有 CSRF token；SameSite 能降低风险，但不应作为唯一防线。
- 没有登录速率限制，存在暴力破解风险。
- 没有密码修改、重置和泄露后的强制下线机制。
- 会话 7 天固定过期，没有滚动续期和过期清理。
- 退出只撤销当前会话，其他设备仍然有效。
- 生产环境若忘记 `COOKIE_SECURE=true`，Cookie 可能通过 HTTP 传输。
- scrypt 参数目前固定，后续可根据部署资源调整；修改参数需要兼容旧哈希。

### 12.3 数据库与迁移风险

- MySQL DDL 非事务性，迁移中途失败可能留下半完成 schema。
- 迁移失败后需要人工检查并修复，不能假设自动回滚。
- `ready` 只检查 `SELECT 1`，schema 未迁移时仍可能返回 200。
- 应用启动不自动迁移，部署脚本必须显式执行 `alembic upgrade head`。
- 测试依赖真实 MySQL；没有 SQLite 兜底，也没有容器化测试环境。
- 测试库重建使用 `drop_all` + `upgrade head`，不适合并行测试 worker。
- 当前 `created_at` 等字段没有 server default，直接 SQL 写入需要显式赋值。

### 12.4 工程管理风险

- 当前 Git `master` 分支尚无任何提交，项目文件全部处于未跟踪状态。
- 建议把本记录点作为第一个 Git 基线提交，避免后续功能开发无法回溯。
- 没有 CI；lint、测试、迁移检查目前靠本地命令。
- 没有 Docker/Compose；新环境需要手工准备 MySQL 和数据库账号。
- `README.md` 的“下一步：论文上传与 PDF 解析”是口语化描述，产品语义应写成“管理员导入论文 + PDF 解析”。
